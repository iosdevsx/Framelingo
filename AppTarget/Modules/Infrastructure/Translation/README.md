# Translation

Это небольшой слой вокруг перевода субтитров. Он задаёт единый формат запроса и ответа, чтобы остальной код не зависел от конкретного сервиса перевода.

## Как устроен пакет

Пакет публикует два продукта:

- `Translation` (`Sources/Api`) — модели и протоколы, которыми пользуются другие модули.
- `TranslationImpl` (`Sources/Impl`) — текущая реализация сервиса и mock-провайдер.

`SubtitleTranslationInput` содержит исходные сегменты, исходный и целевой языки и стиль перевода. Доступны стили `literal`, `natural`, `youtube` и `educational`. Ответ `SubtitleTranslationResult` возвращает массив `SubtitleSegment`.

На уровне API есть два протокола. `TranslationProvider` — граница конкретного движка перевода. `TranslationOrchestrating` — интерфейс сервиса, который вызывает приложение и пайплайн. Сейчас `TranslationService` просто передаёт запрос провайдеру, но это оставляет место для общей логики вокруг разных провайдеров без изменений в вызывающем коде.

## Что реализовано сейчас

Настоящего внешнего переводчика в модуле пока нет. `MockTranslationProvider` ждёт короткое время и записывает в `translatedText` предсказуемую строку с названием языка и стиля. Остальные поля сегмента он сохраняет.

`TranslationAssembly` умеет собрать mock-провайдер, сервис над переданным провайдером или сразу готовый mock-сервис.

Модуль не меняет статус проекта, не сохраняет проект и не проверяет, совпало ли число сегментов. Это ответственность `TranslationPipeline`.

## Обычный поток данных

1. Вызывающий код собирает `SubtitleTranslationInput` из субтитров проекта.
2. `TranslationService` передаёт его выбранному `TranslationProvider`.
3. Провайдер возвращает те же реплики с заполненным `translatedText`.

## Тесты

Тесты подтверждают, что mock сохраняет идентичность, порядок и тайминги реплик, заполняет перевод и что assembly возвращает значения через публичные протоколы.

```sh
swift test --package-path AppTarget/Modules/Infrastructure/Translation
```
