# Документация Framelingo

Это единая точка входа в знания о репозитории. Документация хранится рядом с
кодом, проходит обычный review и проверяется CI. Внешняя вики не является
источником истины.

## Карта источников истины

| Вопрос | Авторитетный источник |
|---|---|
| Что делает продукт и как его запустить | [README проекта](../README.md) |
| Как собрать, протестировать и диагностировать workspace | [Tuist в Framelingo](tuist.md) и [Mise tasks](../.mise.toml) |
| Какие пакеты существуют и от чего зависят | `Package.swift` каждого пакета, общий reader `Scripts/architecture/package_graph.rb` и [сгенерированный снимок](architecture/framelingo-architecture.json) |
| Как проходит runtime-сценарий | [Architecture Site](../Tools/ArchitectureSite/README.md) и `Scripts/architecture/runtime-scenarios.json` |
| Какие зависимости между слоями разрешены | [Architecture policy](architecture-policy.md), `Scripts/architecture/policy.yml` и [границы модулей](module-boundaries.md) |
| Чем владеет конкретный пакет | `README.md` рядом с его `Package.swift` |
| Почему принято важное архитектурное решение | [ADR](decisions/README.md) |
| Какие правила всегда должен соблюдать агент | [AGENTS.md](../AGENTS.md) |
| Что фактически гарантирует поведение | Производственный код и исполняемые тесты |
| Что проверяет CI | [GitHub Actions](../.github/workflows/ci.yml) |

Локальные memories, чаты, handoff-файлы и игнорируемый workspace `openspec/`
могут помогать исследованию, но не являются общими источниками истины в свежем
clone. Если найденное там знание должно пережить текущую задачу, его нужно
перенести в tracked-документ, тест, ADR или автоматическую проверку.

## Типы документации

- **README проекта** — продукт, onboarding и основные команды.
- **README пакета** — ответственность, границы, публичная поверхность и точная
  команда самостоятельного тестирования пакета.
- **How-to** — последовательность действий для конкретной инженерной задачи.
- **Reference** — точные форматы, команды и контракты.
- **Explanation** — устройство системы и причины выбранного подхода.
- **ADR** — одно значимое, долго живущее архитектурное решение.
- **Generated** — факты, извлечённые из manifests и проверяемых source paths;
  такие файлы нельзя править вручную.

## Правила обновления

1. Изменение поведения обновляет тесты и относящуюся к нему документацию в том же
   pull request.
2. Изменение ответственности или зависимости пакета обновляет его README и
   архитектурный снимок.
3. Значимое и труднообратимое архитектурное решение получает ADR.
4. Повторяющаяся ошибка агента превращается в краткое правило `AGENTS.md`, а
   механически проверяемое правило — в audit, test или CI check.
5. Динамические числа и списки пакетов не копируются вручную, если их можно
   получить из manifests или тестового inventory.
6. Перед отправкой изменений запускается `mise run docs:check`.

## Добавление пакета

Новый локальный пакет должен иметь:

- `Package.swift`;
- `README.md` с H1, совпадающим с именем package;
- описание того, чем пакет владеет и чем не владеет;
- раздел `## Тесты`;
- команду `swift test --package-path <путь-к-пакету>`.

Проверка этих минимальных требований автоматизирована. Формулировки и структура
остальных разделов остаются специфичными для конкретного пакета.
